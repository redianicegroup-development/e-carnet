## Contrôles automatisables livrés

```bash
# Sanitation et API
npm run test:api
npm run check:api
(cd apps/api && python3 manage.py makemigrations --check --dry-run)

# Frontend
npm run lint
npm run build

# Smoke mobile/accessibilité local
npm run start --workspace=@ecarnet/web
ops/accessibility-mobile-smoke.sh http://127.0.0.1:3000

# PostgreSQL + backup + restauration isolée + smoke staging
ops/staging-gates.sh reports/staging-gates-current.txt
```

Le script de gates décrit un contrôle Compose local ; le rapport du 05/10 a échoué faute de Docker. La preuve PostgreSQL locale du 08/10 a été obtenue séparément et ne vaut pas exécution de ce script ni recette staging. Quand Docker est disponible, le script :

1. valide `docker compose config` ;
2. démarre PostgreSQL, l’API et le web ;
3. vérifie `pg_isready` ;
4. crée une sauvegarde custom avec SHA-256 ;
5. restaure dans une base isolée sans modifier la base source ;
6. vérifie les migrations restaurées ;
7. vérifie les endpoints readiness et le manifeste des routes.

## Critères de levée du NO-GO

- Exécuter `ops/staging-gates.sh` sur un runner avec Docker Compose et PostgreSQL 16.
- Répéter la restauration avec les sauvegardes de la cible/staging et mesurer le **RPO/RTO opérationnel approuvé** avec un marqueur métier.
- Configurer les domaines, cookies/CSRF, SMTP, Google/Facebook/Apple OAuth et secrets staging.
- Rejouer les parcours mobile Android/Chrome 4G et iOS/Safari avec QR réel.
- Compléter l’audit WCAG 2.2 AA avec axe ou équivalent : focus clavier, contraste, erreurs de formulaire, lecteur d’écran, zoom 200 %, touch targets et session expirée.
- Faire signer la recette staging CA-01 à CA-24 par le responsable produit/sécurité.
- Après ces preuves, remplacer le verdict par **GO** ou **GO CONDITIONNEL** avec les réserves datées.
